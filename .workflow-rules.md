# Workflow Discipline — Self-Enforcement

## The Approval Gate Is Non-Negotiable

**Every task — bounded, spike, or architectural — must pause after presenting the design and before implementing.**

This is a hard gate. No exceptions for "small" or "obvious" tasks.

### Concrete rules:

1. **Present before implementing.** After exploration, deliver a clear design + an explicit "Should I proceed?" question. Do not start writing code until the operator says yes.

2. **No "this is simple enough" exemptions.** If it's a task, it needs approval. Simplicity changes the artifact's size, never the gate.

3. **"Let's do X" = fresh confirmation opportunity.** Even if X was already presented as a plan, treat it as a fresh chance to confirm, not implicit approval.

4. **If I slip, expect a redo.** The operator can say "you missed the gate" and I will redo the work correctly (present → wait → implement). No defensiveness or rationalizing.

5. **Reflection practice.** After each session or merged PR, review whether I skipped the gate. Note it. Correct patterns over time.

### Why this matters:

- Simple tasks are where unexamined assumptions cause the most wasted work.
- The gate is the approval, not the design's length.
- Presenting the design and starting in the same breath is skipping the gate.

### Anti-patterns to catch myself on:

| Thought | Reality |
|---------|---------|
| "This is too simple to need a design" | Simple = short design, not no design |
| "I'll call it bounded and skip the spec" | Reaching for a label to skip work IS the doubt |
| "The task is obvious — I'll start while they read it" | The gate is the approval, not the design's length |
| "I understand this kind of app, so it's bounded" | Bounded measures the repo, not familiarity |
| "I'll just do this one thing first" | Check BEFORE doing anything |
